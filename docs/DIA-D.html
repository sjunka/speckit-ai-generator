Misma constitución que las cinco fases: una sola persona escribe la especificación y reparte los tickets, el resto solo los ejecuta. Ramas y archivos ya están decididos y no se inventan en vivo. Lo único que se escribe a mano es la Historia que dicte el profesor.

Paso 1 — Sergio especifica y reparte · ≈ 5 min · rama main

Es la Fase 1 de siempre: bloquea a todos. Nadie crea su rama hasta que este push termine. Arranca en main al día — git checkout main && git pull origin main.

1.1 — Registra la Historia. Pega esto en el agente, con las historias literales del profesor:

/speckit-specify Agrega dos User Stories nuevas al final de la seccion User Scenarios de
specs/001-ai-media-generator/spec.md, numeradas User Story 5 y User Story 6.
HU 5: "historia literal que dictó el profesor"
HU 6: "segunda historia literal"
Cada una con sus Acceptance Scenarios numerados en formato Given/When/Then.
NO crees una feature nueva. NO corras create-new-feature.sh. NO cambies de rama.
NO toques plan.md ni tasks.md. Solo edita ese spec.md que ya existe.

1.2 — Reparte los tickets. Mismo corte de propiedad que las Fases 2, 3 y 4:

/speckit-tasks Escribe los tres tickets de la HU en vivo en
specs/001-ai-media-generator/hu-viva/: mateo.md, johan.md y tomas.md. Solo esos tres archivos.

Reparte las User Stories 5 y 6 de spec.md con el mismo corte de propiedad que las Fases
2, 3 y 4 de tasks.md: mateo -> app/**/page.jsx y components/**, johan -> app/api/**/route.js,
tomas -> lib/** y test/**.

Cada archivo lleva cuatro secciones:
1. Historia — la parte de la HU que le toca, textual desde spec.md.
2. Criterios de Aceptacion — numerados CA-1, CA-2, CA-3, en formato Dado / Cuando / Entonces.
3. Plan — la lista exacta de archivos que va a crear o modificar, y por que cada uno.
4. Tasks — numeradas, y cada una dice que CA cubre.

Reglas: ningun archivo de codigo puede aparecer en dos secciones Plan. No toques plan.md
ni tasks.md. Si la Historia guarda datos, van a MongoDB por lib/db.js, nunca en memoria.
Si el reparto no cierra, parate y dimelo antes de escribir.

1.3 — Sube las cuatro cosas. Hasta que esto no esté arriba, los demás no tienen ticket. Cuando el push termine, dilo en voz alta:

git add specs/001-ai-media-generator/spec.md specs/001-ai-media-generator/hu-viva/
git commit -m "HU en vivo: User Stories 5 y 6, y los tres tickets repartidos"
git push origin main

Léelo entero antes de pedirle nada al agente. Plan dice exactamente qué archivos puedes tocar; Tasks dice qué CA cubre cada una. Si algo no cuadra, díselo a Sergio ahora — tú no editas el ticket.

2.3 — Implementa test-first (misma sustitución de nombre):

Implementa specs/001-ai-media-generator/hu-viva/mateo.md, test-first:
por cada Criterio de Aceptacion, primero la prueba que falla y despues el codigo que la pasa.

Nombra cada prueba empezando por su criterio: it("CA-2: ...").
Toca unicamente los archivos de la seccion Plan de ese documento. Ninguno mas.
NO edites ese .md, ni spec.md, ni plan.md, ni tasks.md: el ticket ya esta cerrado.
Si un Criterio de Aceptacion esta mal o te falta un archivo, parate y dimelo.
Al terminar corre npm test y dejalo en verde.

Si npm test sale rojo, no hagas push. Dile al agente cuál CA falla, que lo arregle y vuelva a correr npm test. Cuando tu push termine, dilo en voz alta.

Paso 3 — Santiago integra y despliega · ≈ 2 min · rama main

Solo cuando los tres hayan dicho que subieron:

git checkout main
git pull origin main
git fetch origin

Un merge por línea. Espera a que termine cada uno:

git merge --no-ff origin/feature/hu-viva-ui
git merge --no-ff origin/feature/hu-viva-api
git merge --no-ff origin/feature/hu-viva-datos

Si un merge se enreda: git merge --abort y reintenta solo esa rama.

Con los tres adentro:

npm test
npm run build
git push origin main

Ese push despliega en Vercel solo. Mientras construye, proyecta el grafo:

git log --graph --oneline -15
